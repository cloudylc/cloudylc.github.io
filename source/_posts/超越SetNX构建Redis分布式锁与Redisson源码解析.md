# 浅谈一下锁
在计算机领域中，对临界资源的竞争，我们可以使用**锁机制**来保护临界资源。
过程如下：加锁 -> 操作临界资源 -> 解锁

而对于一个健全的锁机制，最基本的也要满足以下2个性质
1. 排他性
2. 活性

排他性强调的是，在同一时刻该有多少个请求者允许拥有锁。
只允许一个则是排它锁。允许多个则是共享锁。

活性强调的是无死锁，即不能让请求都获取不到锁。

而依据请求者颗粒度的不同，也分为不同颗粒度的锁。

对同一个进程间的不同线程而言，这种就属于单机锁，许多编程语言提供了各自的实现。
比如Java的 `Synchronized` 和 `ReentrantLock`。

但对于不同的进程之间，它们可能来自同一个计算机，也可能是不同计算机之间的进程。
此时这些进程去竞争临界资源，这就需要借助**外部**的资源去实现，此时的锁称之为分布式锁。

目前业界主流做法是使用 Redis 或者 Zookeeper 实现分布式锁。
但为了追求性能，更多情况都会使用 Redis 来实现，同时这也是本文的探讨范围。

# 一个简单的分布式锁
一个分布式锁，必然需要包含**加锁**与**解锁**两个功能。

使用 Redis 实现分布式锁中的**加锁**操作，那该操作必须先满足**排他性**。

SetNX 是 Redis 中字符串结构中的一个命令，是英文 SET if **N**ot e**X**ists 的简写。
命令如下：`SETNX key value`
当要设置的`key`**不存在**时，`value`才能设置成功并且返回1。反之设置失败返回0。

当多个进程对同一个`key`执行SetNX命令时，只会有一个进程设置成功，其他的进程都失败。
设置成功的那个进程，就相当于加锁成功了。SetNX 命令它自带排他性。
```
## 成功抢占到锁
127.0.0.1:6379> SETNX product 1
(integer) 1

## 没有抢占到锁
127.0.0.1:6379> SETNX product 1
(integer) 0
```

联想到 SetNX 因 `key` 存在时才设置成功，所以把 `key` 删掉不就是解锁操作了吗！
```
## 删除键
127.0.0.1:6379> DEL product
(integer) 1

## 判断键是否存在，此时锁不存在，解锁成功
127.0.0.1:6379> EXISTS product
(integer) 0

## 此时加锁成功
127.0.0.1:6379> SETNX product 1
(integer) 1
```

就此依靠着`SetNX`与`DEL`命令的配合，就实现了一个**简易**的分布式锁了！

但既然表明它是一个简易的解决方案，那必然存在着诸多漏洞与不足，仍有许多可以优化升级之处。
这便是本文的主旨，在此之上继续探讨可行之道。并且从源码层面，看看Redisson是如何解决的。
